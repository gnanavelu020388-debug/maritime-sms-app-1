## Bug #14 — CRITICAL: Internal staff role restriction was completely bypassed (found & fixed Day 3, user-requested testing of the invite flow)

While testing Super Admin → User & Role Configuration CRUD, invited a new internal staff account ("QA Test Staff") with role **Platform Auditor**, later changed to **Global Support Staff** via Edit. Per user request, tested the invite end-to-end by actually logging in with the one-time temp password issued at creation. The forced "Set a new password" flow worked correctly (confirms the invite mechanism itself is sound) — but after setting a password and landing in the console, the account showed **"Super-Admin"** in the header and sidebar, with full unrestricted access to every section (Tenant & Company Management, Live Provisioning Studio, SMS Documentation, Platform Security & Audits, Billing & Subscriptions, Backups, etc.) despite being assigned the far more restricted "Global Support Staff" role.

**Root cause:** the server (`server/routes/auth.js`) was always correct — it computes `internalRole` from `platform_staff.role` and returns it in both the login and `/api/auth/me` responses. The bug was entirely client-side in `resolveFromApi()` in `src/lib/auth.tsx`: whenever `userObj.role === "super_admin"` (true for every internal-staff login, since all internal accounts carry the coarse `role: "super_admin"` at the transport level — `internalRole` is the actual sub-classification), the function **hardcoded** `internalRole: "super_admin"` and `adminName: "Platform Admin"`, completely discarding the real `internalRole`/`name` fields the server had already sent. This meant the client-side permission model in `src/lib/permissions.ts` (`SECTION_ACCESS`, `capabilitiesFor()` — which correctly restricts Platform Auditor to read-only Security/Audit/Monitoring and Global Support Staff to Tenant/User management only) was never actually being fed the real role, so **every invited internal staff member silently got full Super-Admin access regardless of what role a Super-Admin assigned them** — a genuine privilege-escalation bug, not a cosmetic label issue.

**Fix:** `resolveFromApi()` in `src/lib/auth.tsx` now reads `userObj.internalRole` (typed and passed through from the server response) and only falls back to `"super_admin"` if the server didn't provide one; `adminName` similarly now prefers `userObj.adminName ?? userObj.name` over a hardcoded string.

**Verified live end-to-end:** created a fresh incognito-style tab, logged in as the QA Test Staff account with its temp password, set a new password, and confirmed: (1) header now correctly reads "Global Support Staff" instead of "Super-Admin"; (2) the sidebar now shows lock icons and disables Platform Monitoring, Tenant Backup & Recovery, Tenant Feature Matrix, Live Provisioning Studio, SMS Documentation, Platform Security & Audits, and Billing & Subscriptions — exactly matching the `global_support` role's allowed sections (`tenants`, `users`, `dashboard`) in `permissions.ts`. Deleted the test account afterward via the same 4-step Critical Action wizard used for tenant deletion (Verify → Acknowledge → Confirm phrase → Execute) to leave the platform clean.

Minor unrelated observation (not fixed, low priority): the staff account's Status badge stayed "Invited" even after successfully completing the password-set flow and logging in — likely never transitions to "Active" client-side. Worth a follow-up but far less severe than the RBAC gap above.

## Bug #17 — CRITICAL: "Trigger Tenant Password Reset" silently never worked (found & fixed Day 3, user-reported toast glitch)

User noticed the toast after using Super Admin → User & Role Configuration → Quick Account Actions → "Trigger Tenant Password Reset" read "**undefined** user(s) at Crescent Maritime must set a new password on next sign-in" — asked to find and fix it.

**Root cause — an Express route-shadowing bug in `server/routes/users.js`:** `router.put('/:tenantId/:userId', ...)` (a generic single-user update handler) was registered *before* `router.put('/:tenantId/force-password-reset', ...)`. Express matches routes in registration order, and `:userId` greedily matches any literal path segment — including the literal string `"force-password-reset"`. So every call to the force-reset endpoint was silently being routed into the generic per-user update handler instead, with `userId` bound to the string `"force-password-reset"`. That handler found no recognized fields in the (bodyless) request and returned `{"error":"No fields to update"}` with **HTTP 200** — so the client never saw a failure, just read `result.affected` off an object that didn't have that key, producing `undefined`.

**This meant the entire "force password reset" emergency-security feature had never actually worked** — no user's `must_change_password` flag was ever being set by it, despite the UI always showing a success toast. Verified via a direct authenticated `fetch()` to the endpoint before the fix: response body was `{"error":"No fields to update"}` (HTTP 200) — confirmed the generic handler was intercepting the call, not the intended one.

**Fix:** moved the `force-password-reset` route registration to before the generic `/:tenantId/:userId` route (removed the stale duplicate further down the file), with a comment explaining why the order matters. Verified live: the same direct `fetch()` now returns `{"affected":6}`, and the UI toast correctly reads "6 user(s) at Nordic Reef Services must set a new password on next sign-in."

**Follow-up audit (user asked to check for other missed backend/frontend integration issues):** forked a background audit of route registration order across all 25 files in `server/routes/`, checking every route for this exact shadowing pattern (a wildcard-only route registered before a literal-segment route at the same path depth). Result: **no other instances found** — this was the only occurrence of the bug in the codebase; every other route file already orders literal-segment routes ahead of same-depth wildcard routes correctly.

## Bug #19 — SMS Documentation's "Governance & Override Controls" broke whole-page layout on narrower viewports (found & fixed, user-reported)

After selecting a tenant in SMS Documentation's Inspector Mode, the entire page (not just one component) became horizontally scrollable at the 768px test viewport — content was cut off on the right (including the "Save Tenant Guardrails" button) and a stray page-level horizontal scrollbar appeared, persisting even after scrolling back to the left edge.

**Root cause:** the three-card row (`Workspace Freeze` / `Custom Guardrails` / `Rollback SMS Tree`) used `className="grid gap-4 lg:grid-cols-3"` with no explicit mobile-first `grid-cols-1`. Below the `lg` (1024px) breakpoint this left the grid with no defined column count, so the browser fell back to sizing each `<section>` by its own `max-content` width (CSS Grid items default to `min-width: auto`, which lets intrinsic content width override the container) — with no `min-w-0` guard on the sections, one or more of them (holding sliders, audit-event rows, snapshot buttons) pushed the whole grid, and with it the whole page body, wider than the viewport.

**Fix:** added an explicit `grid-cols-1` before `lg:grid-cols-3` on the grid container, and `min-w-0` on all three `<section>` cards so their content wraps/truncates within the assigned track instead of forcing it wider. Verified live: `document.body.scrollWidth` now exactly equals `window.innerWidth` (768 vs 768, previously overflowing) after selecting a tenant, and all three cards now stack cleanly in a single column with no clipped content or stray page-level scrollbar.

Also checked the adjacent "Document Access & Permissions Matrix" table on the same page, which looked like it might have the same issue (a column labeled "Restricted" was cut off at the screen edge) — confirmed this is *correct* behavior, not a bug: that table already uses the proper contained pattern (`overflow-x-auto` wrapper + `w-full` without `table-fixed`), so only the table itself scrolls horizontally within its own bounds while the page stays fixed-width — exactly the fix pattern used for Bugs #13/#15.
